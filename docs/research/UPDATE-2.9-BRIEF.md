## What changed

1. **`--forward-port PORT` relays one host loopback port into the sandbox (2.9.0, #164).** Without `--network` the sandbox has its own loopback, so a local MCP server, an editor's IDE socket or a dev database on the host's `127.0.0.1` was unreachable, and `--network` was the only way to it. `--forward-port 49374` (repeatable; `forward_ports = [49374]` in the global `~/.ai-jail`) relays exactly that port: the supervisor dials the host's `127.0.0.1:PORT` (falls back to `[::1]:PORT`) over a per-launch Unix socket, and a bridge inside listens on the sandbox's own `127.0.0.1:PORT`. The private network namespace stays up and every other host port stays unreachable. It combines with filtered egress (`--allow-host`) and with `--lockdown` (the port joins the Landlock connect allow set). The agent starts only once every bridge listens; a bridge that cannot bind fails the launch. Refused, fail-closed, in `src/main.rs`: with `--network` ("mutually exclusive: with unrestricted network the host's loopback is already reachable"), outside Linux ("Linux-only"), for port 0 and ports below 1024 ("cannot be bound inside the sandbox"), and for the proxy bridge port. Because `--browser` normally implies `--network`, a `forward_ports` entry in the global base table fails every browser launch and every macOS launch; the README says to put it under a `[commands.<name>]` table. Honest limit (SECURITY.md table): a forwarded port is trusted in full, with no allowlist, inspection or audit record, at most 256 relays at once (`MAX_FORWARD_CONNECTIONS`). Authority: only the CLI and the global config can open one; a project `.ai-jail` can only shrink the list (`project .ai-jail forward_ports ignored`) unless the directory is under `trust_project_config`; auto-save and `--init` never write it to a project file. Listed in `ai-jail --help` as `--forward-port <PORT>`.

2. **Devin is a known agent (2.9.0, #163).** `devin` joins `KNOWN_API_AGENTS` in `src/command.rs` with API host `server.codeium.com`, default-allowed through filtered egress like the other four, unioned with `--allow-host`. Agent state: `$XDG_DATA_HOME/devin` (default `~/.local/share/devin`) and `$XDG_CONFIG_HOME/devin` (default `~/.config/devin`) are shared read-write, login and history included; `--no-agent-state` turns it off. The self-managed installation under `devin/cli/_versions` stays read-only and `cli` cannot be renamed from inside; an absent `cli` (external install) shares state without that protection; a present but invalid `cli` makes Linux share the data root read-only and macOS skip it. Update Devin on the host, then start a new session. README example: `ai-jail devin --permission-mode dangerous`. Devin has no API-key env var (`harness_api_key_env("devin")` is empty).

3. **Codex's default egress adds `chatgpt.com` (2.9.0, #168).** `default_egress_hosts` for `codex` returns `api.openai.com` and `chatgpt.com`, because workspace-backed Codex uses ChatGPT OAuth routing; API-key traffic alone needs only the API host. The other known agents keep one host: `claude` → `api.anthropic.com`, `gemini` → `generativelanguage.googleapis.com`, `grok` → `api.x.ai`, `devin` → `server.codeium.com`. The "one API host" wording on the site is now wrong for Codex.

4. **Fixes (2.9.0):** Codex starts again under macOS Seatbelt: Codex 0.162.1 execs the setuid `/bin/ps`, which Seatbelt refuses, so non-lockdown Codex launches get a private unprivileged `ps` shim (ai-jail's own binary, `src/codex_ps.rs`) answering only that one PID query, plus the macOS services Codex's app-server needs, scoped to Codex; `--no-agent-state` opts out. `--x11` alone now passes X11 through; before 2.9.0 it did nothing without `--display`, silently. Auto-save no longer writes capability opt-ins that an untrusted project file would refuse on reload (`ai-jail --pictures --no-network true` used to leave a warning on every later run); it writes what the project layer's own load accepts, so a saved file never warns, and polluted files clean themselves up.

5. **Documentation (2.9.0, #165), two residual risks now in `docs/SECURITY.md`:** the writable project includes `.git/`, and host-side git trusts it. A program named in `.git/config` (`core.fsmonitor`, `core.pager`) or dropped into `.git/hooks/` runs as you, outside the sandbox, on the next matching host git operation; for `core.fsmonitor` that is a plain `git status`, including one an editor runs in the background. It needs no project code to run and does not show in `git diff`. `--lockdown` closes it (project read-only); `--map .git` keeps the repository read-only in a normal run at the cost of committing from inside. Mapping only `.git/config` and `.git/hooks` stops an accidental write but not a process that renames `.git` and builds a new one. After a surprising session, read `.git/config` and list `.git/hooks` with plain file tools before running git on the host (`git config --list` starts the configured pager). Second: `--mask` and `--deny-path` change what the sandbox sees, not the host files; anything outside acting for the agent (the Docker daemon under `--docker`, an MCP server or broker reached through a mapped socket, now also a service behind `--forward-port`) still reads the real files.

6. Not worth site text: XDG bases for Devin resolved physically with one warning per variable; the `ps` shim reachable through symlinked launch paths; `tests/devin_state.rs` and `tests/port_forward.rs` (integration tests, not in the unit count).
