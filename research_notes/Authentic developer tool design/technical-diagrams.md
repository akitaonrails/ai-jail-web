# Authentic technical diagrams for developer-tool explainers

Research current through 4 October 2026.

## Do isometric neon chip, cloud, and cage illustrations commonly read as generic technology imagery?

### Takeaway

There is no strong published study that isolates the exact “glossy neon isometric chip/cloud/cage” style. The best-supported conclusion is narrower: decorative, interchangeable technology imagery is likely to be skimmed or ignored, while task-relevant graphics that encode real structure attract attention and improve learning. An isometric neon illustration becomes generic when its objects could be swapped between products without changing what the picture teaches.

### Cited Findings

- Nielsen Norman Group’s eye-tracking research distinguishes information-carrying images from “feel-good” or filler images. Users scrutinized images that helped with the task and often ignored generic stock or decorative imagery added to make a page feel exciting. The article was last reviewed in August 2026. [Nielsen Norman Group, “Photos as Web Content”](https://www.nngroup.com/articles/photos-as-web-content/)
- Google’s technical-writing course makes the same distinction with a linked-list example. A polished chain is called “pretty, but information-free” and is also technically misleading because it suggests links in both directions. The preferred schematic explicitly separates each node’s content from its pointer. [Google for Developers, “Illustrating”](https://developers.google.com/tech-writing/two/illustrations)
- Google cites Sung and Mayer’s finding that graphics of any quality can increase readers’ liking of a document, while only instructive graphics improve learning. Google’s practical guidance is to write the caption first, make the figure express that takeaway, constrain each drawing to roughly one paragraph of information, and split complex systems into progressively detailed views. [Google for Developers, “Illustrating”](https://developers.google.com/tech-writing/two/illustrations)
- W3C distinguishes informative images, which require alternatives conveying their essential information, from decorative images, which should use a null alternative because they add no information necessary to understand the page. [W3C WAI Images Tutorial](https://www.w3.org/WAI/tutorials/images/)
- WCAG 2.2 says pure decoration must be implemented so assistive technology can ignore it, while charts, diagrams, pictures, and animations need text alternatives serving the same purpose. Complex diagrams need both a brief identification and a longer equivalent when a short description is insufficient. [W3C, Understanding SC 1.1.1](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html); [W3C WAI, Complex Images](https://www.w3.org/WAI/tutorials/images/complex/)
- Tailscale’s “How Tailscale works” is a useful developer-documentation counterexample to generic hero art. It uses a sequence of restrained schematics, each with a factual caption, to compare hub-and-spoke, multipoint, mesh, coordination, NAT traversal, relays, and distributed ACL enforcement. Each picture changes to carry the next technical claim. [Tailscale, “How Tailscale works”](https://tailscale.com/blog/how-tailscale-works)
- The C4 model recommends multiple levels of zoom that tell different stories to different audiences, and explicitly says teams should use only the diagram levels that add value. [C4 model, “Diagrams”](https://c4model.com/diagrams)
- Google warns that bright colors can pull attention away from the diagram’s meaning, that bidirectional arrows can obscure flow, and that technical figures should be repeatedly simplified. It generally recommends SVG export because it scales without losing quality. [Google for Developers, “Illustrating”](https://developers.google.com/tech-writing/two/illustrations)

### Inferences

- “Generic technology imagery” is best treated as a functional diagnosis rather than an art-style category. If a cage, chip, cube, or cloud does not identify a real boundary, resource, process, route, permission, or failure mode, it behaves like the filler imagery users ignore. This follows from the task-relevance findings, not from a controlled study of neon isometric art specifically. [Nielsen Norman Group](https://www.nngroup.com/articles/photos-as-web-content/); [Google for Developers](https://developers.google.com/tech-writing/two/illustrations)
- Isometric perspective is risky for boundary explanations because depth, overlap, glow, and decorative surfaces compete with the topology. It can also suggest physical containment where Linux actually provides separate namespace views over selected resources. A flat schematic with named boundaries is more falsifiable and easier to check against the product. [Linux namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html); [Google for Developers](https://developers.google.com/tech-writing/two/illustrations)
- A hand-drawn style can feel authored and distinctive, but the authenticity comes from concrete product details, not wobbling lines. A sketch of the actual command, mount path, child process, or denied route is more credible than a hand-drawn generic cloud. This is an inference from the evidence that information relevance, rather than polish alone, drives attention and learning. [Nielsen Norman Group](https://www.nngroup.com/articles/photos-as-web-content/); [Google for Developers](https://developers.google.com/tech-writing/two/illustrations)
- A useful acceptance test is: remove the caption and brand colors, then ask whether a developer can still tell which mechanism is shown and what relationship matters. If the answer is no, the asset is decoration or mood art and should not carry an explanatory burden.
- Decorative art can still establish tone, but it should be sparse, have `alt=""`, and never be the only representation of a boundary or limitation. [W3C WAI Images Tutorial](https://www.w3.org/WAI/tutorials/images/)

### Gaps

- No authoritative usability study found in this research directly compares neon isometric developer-tool illustrations with flat schematics, terminal output, or hand-drawn diagrams.
- “Authenticity” has no standard quantitative metric. The comparison therefore uses inspectability, product specificity, technical fidelity, and resemblance to developers’ actual artifacts as practical proxies.
- The evidence on decorative imagery comes mainly from general web usability and instructional graphics, not specifically from sandbox-tool marketing sites.

## Which diagram forms best explain process trees, filesystem boundaries, network routes, and shared-kernel limits?

### Takeaway

Use the representation closest to the underlying mechanism. HTML/CSS schematics and simple SVGs are the strongest general formats. Pair them with real text artifacts such as terminal output, filesystem trees, and route tables when those artifacts are the mechanism developers inspect. Hand-drawn art is strongest for orientation and narrative; raster terminal screenshots and dense ASCII art are weak defaults because they are harder to adapt, localize, zoom, and read with assistive technology.

### Cited Findings

- Linux defines a namespace as an abstraction around a global resource that gives member processes an isolated instance. The namespace types isolate cgroup roots, IPC, network devices/stacks/ports, mount points, process IDs, clocks, user/group IDs, and host/domain names. [Linux namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html)
- Docker’s introductory documentation states that containers are isolated processes and that multiple containers share the same kernel, unlike virtual machines, which have their own kernels. [Docker Docs, “What is a container?”](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/)
- Docker’s security documentation explains that containers are created with namespaces and control groups; namespaces isolate process and network views, while control groups perform resource accounting and limiting. It also warns that configuration, mounts, capabilities, and kernel vulnerabilities affect isolation. [Docker Engine security](https://docs.docker.com/engine/security/)
- Linux kernel documentation distinguishes shared mounts, slave mounts, private mounts, and unbindable mounts. It uses command transcripts, trees, state tables, and directional propagation examples because mount relationships are not adequately explained by a single enclosing box. [Linux kernel documentation, “Shared Subtrees”](https://docs.kernel.org/filesystems/sharedsubtree.html)
- The `ip route` manual describes the routing table as structured entries with destination prefix, route type, table, next hop, device, metric, scope, and other fields. `ip route show` lists existing entries, while `ip route get` resolves the path as the kernel sees it. [ip-route(8)](https://man7.org/linux/man-pages/man8/ip-route.8.html)
- Tailscale explains network architecture through a sequence of node-link schematics and captions, first comparing routing topologies and then separating control-plane key exchange from data-plane traffic. [Tailscale, “How Tailscale works”](https://tailscale.com/blog/how-tailscale-works)
- W3C says accessible data tables need actual HTML relationships between headers and cells. `<th>`, `<td>`, `scope`, `id`, and `headers` allow assistive technology to preserve row and column context and allow alternative renderings. Tables should describe grid data, not page layout. [W3C WAI Tables Tutorial](https://www.w3.org/WAI/tutorials/tables/)
- WCAG Reflow permits two-dimensional scrolling for diagrams and data tables when the two-dimensional layout is necessary for meaning, but recommends isolating that overflow to the diagram or table rather than forcing the whole page to scroll. It explicitly treats meaningful indentation in nested lists, code, and ASCII art as a case where layout can carry meaning. [W3C, Understanding SC 1.4.10 Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- WCAG treats ASCII art as non-text content even though it is made of characters. ASCII art needs an equivalent explanation and can be given `role="img"`, an accessible name, and a skip link when long. [W3C, Understanding SC 1.1.1](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html); [W3C Technique H86](https://www.w3.org/WAI/WCAG22/Techniques/html/H86)
- WCAG requires meaningful parts of graphics to reach at least 3:1 contrast against adjacent colors and advises against very thin lines because anti-aliasing can make them appear fainter than their nominal color. Color cannot be the only visual carrier of meaning; add labels, shape, pattern, or another visible cue. [W3C, Understanding SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html); [W3C, Understanding SC 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)
- Mermaid can generate SVG with a diagram role description plus `<title>` and `<desc>` elements when the author supplies `accTitle` and `accDescr`. Those features improve naming but do not replace a structured long description for a complex diagram. [Mermaid accessibility options](https://mermaid.js.org/config/accessibility.html); [W3C WAI, Complex Images](https://www.w3.org/WAI/tutorials/images/complex/)
- Graphviz can render a deterministic DOT source to SVG, including inline-ready SVG. Its built-in SVG remains readable and transformable compared with Cairo-rendered output. [Graphviz SVG output](https://graphviz.org/docs/outputs/svg/)
- Google recommends a simple overview followed by separate subsystem figures, captions that state the takeaway, visual callouts that direct attention, and SVG for scalable technical diagrams. [Google for Developers, “Illustrating”](https://developers.google.com/tech-writing/two/illustrations)

### Inferences

The ratings are design inferences grounded in W3C’s requirements for text alternatives, reflow, table semantics, color independence, and contrast, plus Google’s guidance to simplify and use instructive SVG graphics. [W3C Images Tutorial](https://www.w3.org/WAI/tutorials/images/); [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html); [W3C Tables Tutorial](https://www.w3.org/WAI/tutorials/tables/); [Google for Developers](https://developers.google.com/tech-writing/two/illustrations)

#### Best form by technical subject

- **Process trees:** Use a nested semantic list styled as a tree for the primary explanation, with a short real terminal transcript as corroborating evidence. Use SVG only when parent-child relationships cross groups or when launch order matters. Keep node names concrete, such as shell, agent, helper, and child command. A list preserves hierarchy for assistive technology and can stack naturally on mobile; meaningful fixed-width output can remain a secondary LTR artifact. [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html); [W3C, Understanding SC 1.1.1](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html)
- **Filesystem boundaries:** Use an HTML/CSS split or layered map for the concepts “visible,” “read-only,” “writable,” and “hidden,” then a small filesystem tree for exact paths. Encode each state with a label and shape or border, not hue alone. For bind mounts or propagation, add directional arrows in SVG and a short state table because mount topology and filesystem hierarchy are different relationships. [Linux kernel “Shared Subtrees”](https://docs.kernel.org/filesystems/sharedsubtree.html); [W3C Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)
- **Network routes:** Pair a schematic route path with an HTML route table. The schematic answers “where can packets go?” while the table answers “which prefix, next hop, interface, table, and policy produced that result?” A terminal block showing `ip route get` can verify one concrete destination. [ip-route(8)](https://man7.org/linux/man-pages/man8/ip-route.8.html); [W3C Tables Tutorial](https://www.w3.org/WAI/tutorials/tables/)
- **Shared-kernel limits:** Use a flat stacked diagram: multiple isolated process groups and namespace views above one unmistakably shared kernel and one host hardware layer. Label what is isolated separately from what is shared. Do not draw each sandbox as a miniature computer with its own kernel because that teaches the VM model. [Docker, “What is a container?”](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/); [Linux namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html)
- **Layered sandbox controls:** Use a vertical HTML/CSS stack or simple SVG with one row per mechanism, each row naming what it controls and one honest limit. This matches Google’s recommendation to break a complex system into subsystems. [Google for Developers](https://developers.google.com/tech-writing/two/illustrations)
- **Allowed, blocked, opt-in states:** Use a compact HTML matrix or repeated DOM component with explicit state words and consistent symbols. Color can reinforce the state but must not carry it alone. [W3C Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)

### Gaps

- Automated diagram engines differ in RTL support and accessible output. Their current behavior should be tested with the exact pinned version before adoption; the presence of `<title>` and `<desc>` alone does not establish full accessibility.
- No single format wins every criterion. HTML is strongest for adaptation and semantics, while SVG remains necessary for some fixed spatial relationships.
- The performance and bundle cost of a specific client-side diagram library was not benchmarked. A static Astro site should prefer build-time generation or authored inline SVG unless interaction is necessary.

## What implementation guidance applies to a six-language Astro site?

### Takeaway

Adopt a deterministic, data-first diagram system. Keep translatable words in the existing locale catalogs, render them as real HTML or inline SVG text, preserve technical tokens as LTR, provide a visible localized explanation for every complex figure, and build responsive variants from the same structured source. Use raster illustrations only as secondary decoration or when pixels themselves are evidence.

### Cited Findings

- Astro can import local SVG files as inline Astro components. Props such as width, height, fill, and stroke are passed to the underlying `<svg>`. Astro also generates responsive raster variants through `<Image>` and `<Picture>`, but public assets are not processed. [Astro Docs, “Images”](https://docs.astro.build/en/guides/images/)
- Astro requires `alt` on its image components, supports responsive `srcset` and `sizes`, and can emit constrained images that use `max-width: 100%`. [Astro Docs, “Images”](https://docs.astro.build/en/guides/images/)
- Astro’s internationalization routing supports a configured locale list, default locale, locale URL helpers, language fallback, and browser language matching. [Astro Docs, “Internationalization Routing”](https://docs.astro.build/en/guides/internationalization/)
- W3C recommends actual text instead of pictures of text when web technology can produce the presentation, because real text can be resized, recolored, re-spaced, and restyled by users. Diagrams containing significant visual information are not automatically prohibited, but the same textual information must be available when the image is relied on. [W3C, Understanding SC 1.4.5 Images of Text](https://www.w3.org/WAI/WCAG22/Understanding/images-of-text.html)
- W3C says complex diagrams require a short description and a complete textual representation. A visible long description is useful to people with low vision, learning disabilities, and limited subject knowledge, not only screen-reader users. A `<figure>` and `<figcaption>` can group the graphic with a structured long description; `aria-describedby` alone flattens headings and tables into one continuous string. [W3C WAI, Complex Images](https://www.w3.org/WAI/tutorials/images/complex/)
- W3C internationalization guidance says to put `dir="rtl"` on the root HTML element for an RTL document, use `dir` in markup rather than CSS for base direction, and prefer CSS logical start/end properties so layouts localize automatically. It notes that direction also controls table column order and overflow direction. [W3C Internationalization, “Structural markup and right-to-left text in HTML”](https://www.w3.org/International/questions/qa-html-dir)
- CSS logical properties map block and inline dimensions according to writing mode, allowing translated content to follow LTR, RTL, and vertical writing directions without hard-coded left/right assumptions. [MDN, “CSS logical properties and values”](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_logical_properties_and_values)
- WCAG Text Spacing requires HTML/CSS text to survive user overrides to line, paragraph, letter, and word spacing without clipping or overlap. This particularly favors DOM text over tightly fitted labels baked into raster artwork. [W3C, Understanding SC 1.4.12](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)
- GNU gettext recommends preparing complete sentences, splitting at paragraphs, using placeholders rather than string concatenation, and avoiding unusual markup and controls. These practices reduce word-order and translation problems. [GNU gettext manual, “Preparing Translatable Strings”](https://www.gnu.org/software/gettext/manual/html_node/Preparing-Strings.html)
- Mermaid’s accessible title and description fields generate SVG `<title>` and `<desc>` nodes and ARIA references. [Mermaid accessibility options](https://mermaid.js.org/config/accessibility.html)
- The CLI Guidelines recommend human-readable output, plain line-based text for composition, brief output, intentional color, and ASCII only where it increases information density. They also recognize terminal output as a stable, authentic interface that developers inspect directly. [Command Line Interface Guidelines](https://clig.dev/)

### Inferences

#### Recommended architecture

1. **Create one source-of-truth data model per diagram.** Store IDs, state, hierarchy, edges, commands, paths, and technical tokens in TypeScript or JSON. Store every human-language label, caption, short alternative, and long explanation in the six locale catalogs. Generate the HTML/SVG, mobile layout, legend, and textual equivalent from the same IDs. This reduces factual drift and follows the principle of separating information and structure from presentation. [W3C Images of Text](https://www.w3.org/WAI/WCAG22/Understanding/images-of-text.html)
2. **Prefer an Astro component hierarchy over image files.** A practical set would be `SystemMap`, `BoundaryMap`, `ProcessTree`, `FilesystemTree`, `RouteMap`, `RouteTable`, and `TechnicalFigure`. Render static HTML at build time. Use inline SVG only for connectors or fixed geometry that CSS Grid/Flexbox cannot express clearly. Astro’s SVG-component support allows source-controlled assets and prop-driven presentation without a client runtime. [Astro Images](https://docs.astro.build/en/guides/images/)
3. **Make text equivalents visible.** Each complex figure should have a concise localized title or `alt`, a localized caption stating the takeaway, and an adjacent expandable or always-visible “Diagram details” block with headings, lists, or a table. Do not hide all useful explanation in `<desc>` or `aria-describedby`. [W3C WAI Complex Images](https://www.w3.org/WAI/tutorials/images/complex/)
4. **Keep technical artifacts LTR inside every locale.** Commands, shell prompts, flags, IP addresses, paths, route entries, and filesystem trees should use `dir="ltr"`; surrounding captions and prose should inherit the page direction. If a localized annotation is embedded in an LTR artifact, isolate it in a separate DOM element rather than concatenating it into a line. W3C recommends explicit markup for direction and logical CSS for layout. [W3C Internationalization](https://www.w3.org/International/questions/qa-html-dir)
5. **Mirror meaning, not every picture.** A reading-order process may mirror for Hebrew if the chronology is encoded with logical start/end. Protocol artifacts, command pipelines, paths, and network addresses should remain LTR. Geometry that represents physical ingress/egress should be selected intentionally per diagram rather than globally transformed with `scaleX(-1)`, which also reverses text and arrow semantics.
6. **Build two compositions when necessary.** Desktop diagrams can use a two-dimensional layout; mobile should switch to a vertical sequence, stacked cards, or a simplified overview generated from the same data. If spatial meaning requires the wide form, put only that figure in a labelled horizontal-scroll container and provide the reflowing text equivalent immediately below. [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
7. **Use labels and shape in addition to palette.** Keep the site’s stable visual state language, but include explicit “inside,” “blocked,” and “opt-in” text, plus distinct border or icon treatment. Every required line, boundary, node, and state marker should meet 3:1 non-text contrast against adjacent colors; avoid thin glowing strokes. [W3C Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html); [W3C Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
8. **Use terminal output as text, never as a screenshot by default.** Keep output short, remove volatile hostnames, timestamps, usernames, and versions unless they matter, and record the fixture or generator. Add a copy action only when the block is a command the reader should run, not for explanatory output. A screenshot is justified only when teaching a visual UI state. [Astro Images](https://docs.astro.build/en/guides/images/); [Command Line Interface Guidelines](https://clig.dev/)
9. **Treat ASCII as a secondary rendering.** If retained for developer character, wrap it as an image-like object with a localized accessible label, provide a skip link for long art, and include an adjacent semantic equivalent. Keep it LTR and test at 320 CSS pixels and 400% zoom. [W3C Technique H86](https://www.w3.org/WAI/WCAG22/Techniques/html/H86); [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
10. **Pin deterministic generators.** If Mermaid or Graphviz is introduced, render at build time, pin the version, commit source, and either commit output or verify it in CI. Supply localized accessible title/description fields and run visual regression checks for all six locales. [Mermaid accessibility](https://mermaid.js.org/config/accessibility.html); [Graphviz SVG output](https://graphviz.org/docs/outputs/svg/)

#### Localization model

- Give labels stable semantic keys such as `diagram.sharedKernel.hostKernel`, not keys derived from English prose. Translate whole labels and whole explanatory sentences. Do not concatenate “blocked” with a path or build sentences from fragments. [GNU gettext](https://www.gnu.org/software/gettext/manual/html_node/Preparing-Strings.html)
- Keep non-translatable tokens separate: `/home`, `127.0.0.1`, `CLONE_NEWNET`, `--network`, process names, ports, and commands. Render these in `<code dir="ltr">` or `<bdi dir="ltr">` as appropriate.
- Allow labels to grow. Use `minmax()`, `max-inline-size`, wrapping, and intrinsic sizing. Avoid fixed SVG text boxes. WCAG requires that user text-spacing changes not clip or overlap text. [W3C Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)
- For inline SVG, pass localized strings into the component or generate one SVG per locale from common geometry. Use SVG `<text>` only for short labels; put paragraphs, lists, and detailed explanations in HTML. Include unique localized `<title>` and `<desc>` IDs per rendered instance. [Mermaid accessibility](https://mermaid.js.org/config/accessibility.html); [W3C WAI Complex Images](https://www.w3.org/WAI/tutorials/images/complex/)
- Test pseudo-localized expansion before human translation, then inspect real Hebrew, Japanese, and Korean. Hebrew must be reviewed for bidi punctuation, mixed code tokens, arrow direction, focus order, and overflow. Japanese and Korean need review for line breaks and compact label fit. CSS logical properties reduce layout forks but do not validate semantics by themselves. [W3C Internationalization](https://www.w3.org/International/questions/qa-html-dir); [MDN logical properties](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_logical_properties_and_values)

#### Suggested content set for this site

- **Shared kernel:** HTML/CSS stack with three sandboxed process groups above one shared kernel. Add an adjacent two-column list: isolated views versus shared host/kernel realities.
- **Filesystem:** Semantic tree showing only a handful of representative paths, with visible state badges for writable, read-only, and hidden. Follow with a short terminal block that demonstrates one denied path.
- **Network:** SVG or HTML route map with numbered hops, plus an HTML route table and a concrete `ip route get` example. Numbered hops work without color and survive translation better than arrow labels.
- **Process scope:** Nested semantic process tree, optionally paired with a real normalized `ps`-style transcript. Avoid decorative “agent inside a glowing chip” imagery because it does not reveal parent-child ownership.
- **Security limits:** Flat comparison of namespace isolation and shared-kernel exposure, with a direct link to the canonical security explanation. Avoid drawing a fully sealed cage because the picture would imply a stronger boundary than the product claims.
- **Brand expression:** Put personality in line weight, border rhythm, typography, spacing, and the existing warm/cyan state system. Reserve hand-drawn marks for small editorial callouts or overview figures where precision is not compromised.

#### Verification checklist

- At 320 CSS pixels, no page-level horizontal scrolling; any wide route table or necessary diagram scrolls only inside its labelled container. [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- At 200% and 400% zoom, labels remain readable, are not clipped, and do not overlap; text-spacing overrides also preserve content. [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html); [W3C Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)
- With CSS disabled, HTML diagram reading order and the textual equivalent still explain the mechanism.
- With color removed, labels, patterns, borders, and symbols still distinguish every state. [W3C Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)
- Required graphical objects meet 3:1 contrast; text meets the applicable text contrast criterion; lines are not hairline-thin. [W3C Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
- Screen-reader review reaches a concise figure name and a complete, structured explanation without reading decorative connector paths or every SVG group.
- Keyboard focus order follows the logical explanation order if a diagram contains links, toggles, or an expandable description.
- Every locale has a real localized caption, accessible name, and long description. No diagram silently falls back to English.
- Hebrew page direction is RTL while terminals, paths, addresses, and protocol diagrams that are inherently LTR remain explicitly LTR. [W3C Internationalization](https://www.w3.org/International/questions/qa-html-dir)
- Generated SVG output is reproducible, source-controlled, and visually reviewed after dependency changes.
- Each figure passes a factual review: every node, line, direction, boundary, and state corresponds to a documented product behavior.

### Gaps

- This research did not inspect assistive-technology behavior for a prototype implementation. Inline SVG accessibility varies by browser and screen-reader combination, so the final component needs empirical testing.
- No performance benchmark was run comparing inline SVG, static external SVG, HTML/CSS, and responsive raster output in this Astro build.
- The ideal amount of hand-drawn character is a brand decision that should be tested with representative developers. The evidence supports task relevance and technical specificity, not one universal visual style.
- Before implementation, validate candidate diagrams with at least one reader unfamiliar with the product. Ask them to state the boundary, route, or limit the figure communicates; visual preference alone is not enough.
